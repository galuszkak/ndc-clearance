# AGENTS.md — NDC Clearance

## Project overview

NDC Clearance is an interactive browser, validator and diff tool for IATA NDC (New Distribution Capability) XML schemas. It serves airlines, travel agents and developers working with the standard.

Capabilities:

- Hierarchical schema browsing and full-text search across elements, types and documentation
- Static version comparisons with CSV export
- Backend XML validation against a selected schema release
- Canonical IATA and custom XML examples shared by the site and backend
- Interactive flow graphs with examples associated with each published step
- MCP tools for schema discovery, retrieval, validation and examples

Live site: https://ndc-clearance.netlify.app

Public MCP endpoint: https://mcp-ndc.sunrisehikers.io/mcp/sse

## Repository structure

The three subprojects have independent builds. Run commands from the relevant subdirectory.

```text
ndc-clearance/
├── site/                    # Astro + Svelte static frontend
├── backend/                 # Kotlin/Ktor REST and MCP server; diff generator
├── tools/                   # Kotlin CLI schema and content tools
├── raw_ndc_schemas/         # Original extracted IATA XSD sources
├── ndc_schemas/             # Generated schemas grouped by version/message
├── ndc_diffs/               # Generated gzipped JSON version comparisons
├── ndc_content/             # Canonical examples, source metadata and flows
├── .github/workflows/       # CI and deployment
├── podman-compose.yml       # Container definitions; see README limitations
├── iata_ndc_messages.json   # Registered releases and messages
```

Treat build/cache directories and copied runtime assets as disposable; do not commit them. Flattened schemas in `ndc_schemas/` are tracked: generate them locally and commit them with the corresponding raw sources and message-map changes. Static diffs in `ndc_diffs/` remain uncommitted build artifacts. Canonical `ndc_content/examples/catalog.json` and `ndc_content/flows/flows.json` are tracked outputs: regenerate them through the content tools and review their changes. `flows.json` also holds custom flow definitions.

## Frontend: `site/`

### Architecture

Astro static generation with Svelte runes for interactive islands, Tailwind CSS and DaisyUI for styling, `@xyflow/svelte` and Dagre for flow graphs, highlight.js for XML, and the Astro sitemap integration. TypeScript uses the strict Astro configuration. ESLint, Prettier, Vitest and Testing Library provide checks.

### Commands and assets

Read `package.json` for scripts. Run `npm ci` before using them.

- `npm run dev` starts the development server on port **4321**.
- `npm run check` runs Astro diagnostics. Run it before considering site changes done.
- `npm run lint`, `npm run test` and `npm run build` provide lint, unit tests and a production build.
- `npm run copy-assets` invokes `copy-schemas`, `copy-content` and `copy-diffs`. Both `dev` and `build` invoke it first.

Asset copies:

| Source | Destination |
|---|---|
| `../ndc_schemas/` | `public/schemas/` |
| `../ndc_content/examples/` | `public/content/examples/` |
| `../ndc_content/flows/` | `public/content/flows/` |
| `../ndc_diffs/` | `public/diffs/` |

Re-run the copy step after changing source data during development. Flow pages also read canonical `ndc_content/flows/flows.json` during static generation.

The diff viewer reads `/diffs/diff_{from}_to_{to}.json.gz`, generated by `backend/`'s `precomputeDiffs` task. It decompresses gzip in the browser and inverts results for reverse comparisons. It does not call the REST diff endpoint. Missing precomputed files do not fail the site build, but comparisons will be unavailable.

`src/utils/config.ts` defines `API_URL` and `MCP_URL`, overridden at dev/build time by `PUBLIC_API_URL` and `PUBLIC_MCP_URL`. The API defaults to the local backend; MCP setup links default to the public service.

## Backend: `backend/`

### Architecture and local commands

Kotlin with Ktor/Netty, the Kotlin MCP SDK, kotlinx serialization, JVM XML Schema validation and optional PostHog analytics. The build produces a shadow JAR. Read the build file and wrapper properties for versions and the required JDK.

Use the committed schemas, regenerating them locally with the tooling after source changes. From `backend/`:

```bash
SCHEMA_ROOT=../ndc_schemas CONTENT_ROOT=../ndc_content ./gradlew run
SCHEMA_ROOT=../ndc_schemas CONTENT_ROOT=../ndc_content ./gradlew test
./gradlew shadowJar
./gradlew precomputeDiffs
```

`precomputeDiffs` reads `../ndc_schemas` and writes `../ndc_diffs` as configured in the Gradle task; it does not use `SCHEMA_ROOT`.

| Environment variable | Default | Purpose |
|---|---|---|
| `PORT` | `8080` | HTTP port |
| `SCHEMA_ROOT` | `src/main/resources/schemas` | Schema filesystem root |
| `CONTENT_ROOT` | `src/main/resources/content` | Content root containing `examples/catalog.json` |
| `POSTHOG_API_KEY` | Unset | Optional backend analytics |

The default data paths require a sync, as CI performs. CORS allows any host by design; do not restrict it without discussion.

### API and MCP

| Method | Path | Purpose |
|---|---|---|
| GET | `/` | Redirect to the public site |
| GET | `/schemas` | List indexed versions and messages |
| POST | `/validate` | Validate `{version, message, xml}` |
| GET | `/api/diff` | Compare `?from=<version>&to=<version>` |

Schema lookup uses directory message names such as `AirShoppingRQ`, without the `IATA_` prefix. New releases are discovered from directories; there is no runtime version allowlist to update.

MCP tools at `/mcp/sse`: `validate_ndc_xml`, `list_versions`, `list_schemas`, `get_schema_files`, `list_examples` and `get_example_content`. Example listing accepts optional message/version filters; content lookup uses `example_id` and optional `include_metadata`. No filters returns all active examples. There are no REST example/flow endpoints or dedicated MCP flow tools.

Registered releases without a schema directory are not shipped and do not become test cases. ## Tooling: `tools/`

Kotlin CLI tools using Jsoup, the JDK HTTP client, XML APIs and kotlinx serialization. Read `build.gradle.kts` and the Gradle wrapper for the toolchain and dependency versions.

### Commands

Run from `tools/`:

```bash
# Replace placeholders with a registered release and local archive.
NDC_RELEASE='<registered-release>'
NDC_ARCHIVE='../<iata-release-archive>.zip'
./gradlew importSchemas --args="--version=$NDC_RELEASE --archive=\"$NDC_ARCHIVE\""
./gradlew flatten --args="--version=$NDC_RELEASE"
```

| Command | Purpose |
|---|---|
| `./gradlew flatten` | Flatten all registered releases with available raw sources |
| `./gradlew download` | Fetch IATA example XML and example/flow source metadata |
| `./gradlew buildContentCatalog` | Rebuild the example catalog and merge IATA/custom flows |
| `./gradlew validate` | Validate downloaded IATA examples against flattened schemas |
| `./gradlew validate --args='--schema-type=raw'` | Validate against raw schemas |
| `./gradlew analyzeMissing` | Report message/example coverage gaps |
| `./gradlew validateFlows` | Check flow message names against the baseline selected in `ValidateFlows.kt` |
| `./gradlew verifyFlowCoverage` | Check nonempty example IDs for every flow step |
| `./gradlew test` | Run tooling unit and schema integration tests |

`validateFlows` and `verifyFlowCoverage` are standalone tasks; `buildContentCatalog` does not invoke them. The worked-example validator reports missing/unmapped schemas separately; a successful exit alone does not prove every input was validated. Inspect the coverage report.

It writes only to temporary directories. New registered releases with raw sources are included automatically; no per-release test class or message count is needed.

### Release import process

1. Inspect the ZIP and verify the NDC message list, distinguishing unrelated standards and API specifications.
2. Register the release and messages in `iata_ndc_messages.json`.
3. Import registered messages and dependencies into `raw_ndc_schemas/{version}_ndc/`. Preserve original XSD bytes and record provenance. The importer supports sibling XSD dependencies, rejects ambiguous/missing files and refuses conflicting existing sources.
4. Flatten locally, test raw and generated schema compilation, and verify backend discovery/validation/diffs. Review and commit the raw sources, message-map changes and flattened schemas together.
5. Regenerate static diffs and refresh site assets.

Schema-internal IDs need not match the release label. Do not rename or reinterpret original attributes. Add worked-example schema-ID mappings only when verified from actual examples; do not relabel existing examples or flows to match a new release.

Batch flattening skips versions with no matching raw source directory. A specifically requested version must exist. Missing registered message files and unreadable schemas fail the task.

## Canonical content and data flow

```text
IATA ZIP → importSchemas → raw_ndc_schemas/ → local flatten → ndc_schemas/ (committed)
                                                        ├→ site/public/schemas/
                                                        ├→ backend resource sync
                                                        └→ precomputeDiffs → ndc_diffs/ → site/public/diffs/

IATA pages → download → examples/files/iata/ + examples/sources/iata.generated.json
                     └→ flows/sources/iata.generated.json

IATA/custom example sources + flow definitions → buildContentCatalog
    ├→ ndc_content/examples/catalog.json
    └→ ndc_content/flows/flows.json
          ├→ site/public/content/ (copy-assets)
          └→ backend resources (CI sync)
```

Content conventions:

- Add custom XML under `ndc_content/examples/files/custom/` and metadata in `examples/sources/custom.json`.
- Default example IDs are deterministic hashes; explicit source IDs are also supported. Preserve identifiers when editing metadata.
- Flow records use `id` as the route slug, with stable `step_id` references. Catalog examples use nullable `flow_id` for association. These are distinct fields.
- Generated IATA slugs come from titles. Never rename existing flow IDs/slugs casually: links and references depend on them. Explicit example assignments take precedence over inferred IATA page/URL identifiers.
- `buildContentCatalog` writes the catalog, then rewrites `flows.json` with generated IATA flows and custom records. Flows marked `status: "iata"` are regenerated; use `status: "custom"` for custom definitions/overrides. Custom IDs take precedence on collisions with generated flows.
- The merge drops nonempty flows with less than **100% step-to-example coverage**. This is association coverage, not XML-validation coverage. Flows are stored in `flows.json`, not embedded in `catalog.json`.
- Catalog construction checks existing references, message consistency, duplicate IDs and conflicting example assignments. Review both tracked outputs after a build; do not hand-edit the catalog to bypass source changes.

## CI and deployment

Workflows are path-filtered. Both deployments run on matching pushes to `main`; tooling checks also run on matching pull requests. Read workflow YAML for exact filters, action versions and toolchains.

| Workflow | Checks and preparation | Destination |
|---|---|---|
| `ci-tools.yml` | Tooling tests and canonical catalog build | No deployment |
| `deploy-site.yml` | Precompute diffs from committed schemas, install dependencies, lint, test and build | Netlify |
| `deploy-backend.yml` | Sync committed schemas/content, test and build shadow JAR | Unikraft Cloud |

The site workflow sets the public backend API URL at build time. Committed flattened schema changes trigger both deployments. Raw schema and tooling changes trigger tooling checks; deployment workflows do not regenerate flattened schemas. Backend implementation changes do not currently trigger the site workflow, so changes affecting static diff output also need a site rebuild.

Secrets: `UKC_TOKEN`, `UKC_DEPLOYMENT_NAME`, `UKC_METRO`, `POSTHOG_API_KEY`, `NETLIFY_AUTH_TOKEN`, `NETLIFY_SITE_ID`. Never commit them.

Docker Compose is not a complete fresh-checkout workflow: the site image omits canonical content/diffs, and the backend image requires synced schemas and lacks runtime content configuration. See README for the current limitations; do not claim full container functionality without checking those paths.

## Development rules and boundaries

- Use ESLint/Prettier conventions for site code: four-space indentation, semicolons and trailing commas. Avoid `console.log`; the lint rule warns on console use. Prefix intentionally unused variables with `_`.
- Use Svelte runes for new component state. `stores.ts` is legacy schema-statistics state, not a pattern for new components.
- Follow Kotlin conventions and keep the backend minimal.
- Preserve lazy schema resolution and multi-file XSD support. Common types and external dependencies are part of a message's schema bundle.
- Do not edit generated schemas, diffs or copied assets in place. Use `flatten`, `precomputeDiffs`, `copy-assets` and CI sync. This includes `ndc_schemas/`, `ndc_diffs/`, `site/public/{schemas,content,diffs}/` and `backend/src/main/resources/{schemas,content}/`.
- Commit locally generated `ndc_schemas/` outputs with schema source changes. Do not hand-edit them. Do not commit static diffs, copied runtime assets, build outputs, caches, `node_modules/`, `dist/` or secrets. Review regenerated canonical content separately from runtime copies.
- Do not restrict the intentionally open backend CORS policy without discussion.
